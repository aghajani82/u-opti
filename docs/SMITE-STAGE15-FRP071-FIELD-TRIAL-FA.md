# نصب آزمایشی یکپارچه IR/KH — FRP 0.71.0 و WSS

این مسیر Production نیست. هیچ تغییر زنده‌ای در تهیه این بسته روی IR/KH یا Grandoptical انجام نشده است.
نصب و اتصال واقعی دو VPS، XHTTP کلاینت و reboot هنوز باید با مجوز اپراتور آزمایش شوند.

## منشأ ایمیج‌ها

Workflow `40830661751`، Artifact `12878322384`، معماری ایمیج‌ها amd64.
Manifest SHA256: `0b34ee3fbd9174e6bf7ef6ddf145f7ebcd606c9bbeae176bb3d6a38b8a2a7840`.

- Panel: `sha256:e2345c7a4bf17cd9507ecf065cc736f4c2abfbe276a8c334805f4e52bb3808b5`
- Node: `sha256:cf0f3b12fc2c31cb0847fd5206304837661019d8f604853a8e956448c2576265`

هش رسمی FRP هر معماری پیش از استخراج بررسی می‌شود. CI بایت باینری‌های داخل ایمیج را با آرشیو رسمی مقایسه می‌کند.
WSS با CA سیستم و نام دامنه پنل اعتبارسنجی می‌شود. گواهی نامعتبر، SNI اشتباه و Token اشتباه در آزمون واقعی ایزوله رد شده‌اند.
شناسه‌ها متعلق به Docker/containerd آزمایش‌شده‌اند؛ در صورت اختلاف ID پس از Load، نصب باید HOLD شود، نه اینکه شناسه دستی جایگزین شود.

## نصب تازه؛ فقط پس از Snapshot و دسترسی Console

ابتدا SHA256 فایل ZIP را با فایل checksum کنار آن تطبیق دهید؛ بعد از استخراج، `SHA256SUMS` تمام فایل‌های داخل بسته را بررسی کنید.
روی هر میزبان نام کوتاه باید `ir` یا `kh` باشد. Grandoptical خارج از دامنه است.

**IR:** `bash start.sh IR`

1. در ویزارد Clean-RC، Panel + Iran Node را نصب کنید و دامنه پنل را بدهید؛ TLS و ورودی 443 را بررسی کنید.
2. از مسیر Signed Pairing، نود ایران را رزرو و کد یک‌بارمصرف را Redeem و Signed Runtime را فعال کنید.
3. Connected بودن نود ایران را در پنل بررسی کنید؛ نصب مجدد یا تولید دوباره هویت لازم نیست.

**KH:** `bash start.sh KH`

1. Foreign Node را با دامنه پنل ایران نصب کنید.
2. Sanaei را از Docker Management نصب کنید یا کانتینر موجود را انتخاب کنید؛ اتصال اطلاعات آن به Node فقط‌خواندنی است.
3. Gateway خارج روی HTTPS/443 را از ویزارد تنظیم کنید؛ API نود روی 127.0.0.1:8888 باقی می‌ماند.
4. در پنل ایران، نود KH را رزرو و Origin دقیق آن را تأیید کنید؛ سپس کد را روی KH Redeem و Signed Activation را اجرا کنید.
5. هر دو نود باید Connected باشند. در هیچ مرحله‌ای Legacy را فعال نکنید.

در نصب Core هیچ پورت یا مسیر تانلی لازم نیست.

## نصب FRP و فعال‌سازی WSS

مسیر منو: Smite Management → Independent Engines → FRP → گزینه 3 (Stage15).
این منو به نصب Backhaul وابسته نیست؛ از گزینه قدیمی RC2 Publish برای این ایمیج استفاده نکنید.

1. **BOTH:** گزینه 1، نصب FRP. فایل رسمی معماری میزبان از `dependencies` بسته انتخاب می‌شود. Snapshot/Console را صریحاً تأیید کنید.
2. **BOTH:** گزینه 2، فعال‌سازی Signed WSS. این کار تانل ایجاد نمی‌کند. IR همچنین تنظیم WSS پنل را اعمال و Backup سازگار SQLite تهیه می‌کند.
3. **IR:** گزینه 3، ابتدا Bridge مسیرهای Signed و سپس لبه WSS/443؛ فقط IPv4 خروجی واقعی و تأییدشده KH را وارد کنید. SNI و IP مبدأ باید هر دو تطبیق داشته باشند.
4. **BOTH:** گزینه 4، بررسی امضا و Replay. سپس وضعیت هر دو نود را در پنل بررسی کنید.

پورت‌های 7000 و 8888 را در فایروال عمومی باز نکنید. FRPS و پورت‌های Proxy روی loopback قرار می‌گیرند.
Backend اصلی پنل حفظ می‌شود؛ فقط اتصال SNI+IP مجاز KH به Backend مجزای WSS می‌رود.

## پورت، XHTTP و Owner/Child؛ پس از نصب Core

- در Sanaei روی KH، Inbound موردنظر را روی `127.0.0.1` با پورت آزاد و Path انتخابی خودتان بسازید. انتخاب این دو هنوز ورودی اپراتور است.
- در Smite، نخستین FRP TCP را با IR به‌عنوان Server، KH به‌عنوان Client و control port برابر 7000 بسازید؛ Local IP باید 127.0.0.1 باشد.
- برای پورت اضافی، همان Owner را صریحاً انتخاب کنید؛ Child نباید FRPS دوم بسازد. پنل مالکیت و Listener را با درخواست Signed بررسی می‌کند.
- انتشار XHTTP از مسیر Signed Inventory/Route Intent پنل و Root Broker انجام می‌شود. از گزینه `G` همین منو، Grant ریشه را برای Child، نود، دامنه و محدوده دقیق مجاز صریحاً تأیید کنید؛ نبود Grant باید HOLD بدهد.
- این بسته Grant باز یا wildcard نمی‌سازد. کشف Inbound و اعتبارسنجی Intent خودکارند؛ انتخاب Inbound/Path و تأیید Grant همچنان دستی‌اند.
- قبل از اعلام آمادگی، ترافیک واقعی کلاینت، رد مسیر غیرمجاز، اتصال دوباره پس از reboot هر دو میزبان و حفظ Replay را بررسی کنید.

## ارتقای نصب موجود بدون Rebuild

برای نصب موجودِ Signed و Connected از نصب Clean-RC دوباره استفاده نکنید.
در منوی Stage15 FRP گزینه `U` را انتخاب کنید؛ بدون مسیر دستی، پوشه تصاویر معتبر از Release دریافت/از کش استفاده می‌شود. برای بررسی جداگانه گزینه `D` وجود دارد. این ارتقا فقط زوج اصلی Stage15 شناخته‌شده را می‌پذیرد؛
قبل از ارتقا باید FRP/WSS و تمام تانل‌ها غیرفعال باشند. حداقل 4 GiB فضای آزاد برای Backup لازم است.

قبل از Load/Recreate: Backup ایمیج اصلی، هویت، SQLite Replay و روی IR دیتابیس پنل در پوشه خصوصی 0700 با فایل‌های 0600 ذخیره می‌شود.
با خطا، tag و Runtime قبلی بازگردانده می‌شوند. هیچ دیتابیس زنده یا Replay با Backup بازنویسی نمی‌شود.
پس از موفقیت، گزینه‌های نصب FRP و WSS را طی کنید. پاک‌سازی Image قدیمی/Backup پیش از پذیرش تست واقعی ممنوع است.

Rollback: ابتدا Childها و سپس Owner را از پنل حذف کنید؛ روی IR لبه WSS را با گزینه 6 برگردانید؛
روی BOTH گزینه 5 برای WSS، سپس گزینه 9 برای FRP. برای بازگرداندن ایمیج، گزینه `R` را انتخاب کنید.
در قطع عملیات، گزینه Recover همان تراکنش را اجرا کنید. در تغییر خارجی فایل‌ها، حالت HOLD و حفظ شواهد عمدی است.

## حدود آزمایش و وابستگی‌ها

آزمون Host Executor از فایل‌سیستم واقعی موقت و Docker شبیه‌سازی‌شده استفاده می‌کند؛
آزمون‌های Docker/Compose، امضا، Replay و FRP/Nginx/TLS واقعی در GitHub Actions جداگانه اجرا می‌شوند.
این‌ها جای آزمون کامل Ubuntu و دو VPS واقعی را نمی‌گیرند.

بسته شامل سورس دقیق، ایمیج‌های Panel/Node، آرشیو رسمی FRP، Manifest و checksum است.
Ubuntu apt، Docker/Compose، Nginx/Certbot، صدور گواهی و Sanaei همچنان اینترنت لازم دارند.
باینری FRP arm64 موجود است، اما ایمیج این زوج فقط amd64 است.
